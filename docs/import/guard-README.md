# Ticket 20: personal guard

This unactivated personal pi extension protects against **accidental agent mistakes, not a determined agent**. On 2026-09-24 the owner decided that git/GitHub commands, every tool, and every project resource are allowed, without role distinctions or project trust warnings.

It does three things in every session and role:

1. Refuses `model` fields selecting a model on the subagent ban list (case-insensitive substring, thinking suffix stripped), including nested subagent task, chain and workflow step fields, using `isProhibitedModel`. The list is `harness.subagentBanList` in the personal settings file, `fable` and `astra` when absent (ticket 21, see `harness/README.md`). The subagent ban list does **not** ban the session's own model. The separate session ban list, `harness.sessionBanList`, empty by default, binds only the session model: when the session starts on, or switches to, a model on that list, the guard reports `session model '<id>' is on the session ban list (entry '<entry>'); no turn runs until another model is selected.` Until an allowed model is selected it swallows every submitted prompt (`input`) and aborts every other turn at `turn_start`, before the provider is called; that covers turns an extension starts with `sendMessage(..., { triggerTurn: true })`, which is how pi-subagents delivers async completions. pi cannot cancel a model selection, so blocking the turn is the refusal. In print mode a blocked `pi -p` run exits 0 with the refusal only on stderr. The session check is skipped in processes that host delegated sessions, marked by pi-subagents with `PI_SUBAGENT_CHILD=1` (the async runner) or `PI_SUBAGENTS_HERDR_BRIDGE=1` (a herdr pane-native child): ambient extensions load into those children, and a delegated agent is not the orchestrator's session. Foreground subagents run in the parent process with ambient extensions off, so the guard never sees their session. Other keys such as `dataModel`, prose, file paths and bash command text are never model selections.
2. Refuses `write`/`edit` paths canonically inside the agent directory, including symlink aliases, `~`, and case-equivalent paths on case-insensitive volumes. **Bash commands are not path-checked or wrapped and can still write anywhere, including the agent directory.** The guard offers no shell write protection.
3. Refuses a simple nested `pi` invocation whose executable is `pi` and whose arguments disable extensions (`-ne` or `--no-extensions`) or select a different `PI_CODING_AGENT_DIR`. Simple `sh -c` payloads and `env` prefixes are inspected. Ordinary `pi` and canonical spellings of the same agent directory, including `$HOME`, `${HOME}`, `~` and case aliases on case-insensitive volumes, are allowed. Quoted examples and heredoc text are not executable pi commands. The flag check also refuses `pi -ne --help` and `pi -ne --version`.

The guard reads both lists at load and again at each session start, when the project cwd is known. Each personal key is checked on its own: a valid key is kept when the other is bad, and a malformed list keeps its defaults plus its usable entries, so a bad edit can only narrow. An unreadable personal file keeps the defaults; an unreadable or invalid project settings file keeps the personal lists. Either failure logs one line, `pi-orchestration-harness guard: ban lists: <error>`, and the guard keeps running. A project `.pi/settings.json` carrying `harness.subagentBanList` or `harness.sessionBanList` changes nothing; the guard logs `pi-orchestration-harness guard: ignored project settings key <key>` once per key. With `PI_HARNESS_GUARD_PROBE=1` it also prints the effective lists at session start.

There is no tool allowlist, project inspection, owner agreement file, or approval-action gate. `mcp`, `ctx_execute`, `web_search`, `contact_supervisor`, project `.pi/extensions` and `SYSTEM.md`, ancestor `.agents/skills`, `git push`, and `rm -rf` are permitted.

Known ways around this mistake guard: **bash can write anywhere**; a session-banned session model inside a process that carries a pi-subagents child marker (see point 1); `ctx_execute`, MCP, or other extensions' own processes can write; editing the guard source in the repo; renaming ancestor directories; git hooks and shell rc scripts; a crash or load failure disables the guard; and owner bypasses including `pi -ne`, `pi --no-extensions`, `pi --approve`, or another `PI_CODING_AGENT_DIR`. The nested-pi detector is not a complete shell parser. When an import or runtime check fails, the guard logs `harness guard disabled: <reason>` once and pi continues. To recover, start pi with `pi --no-extensions` and repair the checkout, or uninstall the owned entry:

```sh
node harness/guard/activate.ts uninstall --agent-dir ~/.pi/agent --owner-confirm-real-agent-dir
```

## Activation

Install and rollback are deliberate, never import side effects. The gate is shared with the router extension (ticket 27, `harness/activation/extension-gate.ts`); each has its own entry, probe variable and activation marker:

```sh
PI_HARNESS_LIVE_MODEL=anthropic/claude-haiku-4-5 node harness/guard/activate.ts install --agent-dir /path/to/throwaway-agent
PI_HARNESS_LIVE_MODEL=anthropic/claude-haiku-4-5 node harness/guard/activate.ts install --agent-dir ~/.pi/agent --owner-confirm-real-agent-dir
```

Activation requires `PI_HARNESS_LIVE_MODEL`, runs typecheck and the full suite, and refuses failures or **any skips**. The suite receives `PI_HARNESS_GUARD_ACTIVATION=1`; nested activation refuses immediately rather than running another suite. Main now has an Anthropic route, so zero skips should be achievable after merge. It verifies loading in real pi after writing and removes its entry on failed verification or probe. A temporary or linked-worktree checkout is refused. Canonical comparison requires the owner flag even for aliases of the real agent directory. Rollback removes only its own exact entry. **The guard is not activated** in the real agent directory.
